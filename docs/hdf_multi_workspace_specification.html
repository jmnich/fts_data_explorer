1. Overview

A multi-workspace container (file extension .cross.h5) holds many single-dataset workspaces plus the cross-workspace artifacts built on top of them. It is the project file the application opens when a user works with several datasets at once.

Each embedded workspace is a complete unified-spectral-data-container — raw measurements, computed spectra, and per-panel view state — stored byte-identically under a sources/<id>/ group. The container adds three things the single-dataset format does not have:

  • An archive manifest (archive.json) that is the single source of truth for what the archive contains.
  • Cross-workspace experiments (experiments/<id>/) — Absorbance and Comparator analyses that overlay artifacts from one or more embedded datasets.
  • Batch-processing recipes (recipes/) — reusable processing parameter sets that can be applied across datasets.

The inner layout of each embedded workspace is specified by the Single-Dataset Specification; this document does not repeat it.

2. Format rules

#Rule
1The container has no root @format attribute. This distinguishes it from a single-dataset .h5, which always carries @format = "unified-spectral-data-container". The archive.json dataset at the root is the discriminator (see §9).
2archive.json is the source of truth. The list of sources, experiments, and the tab-strip order live in the manifest. Group existence on disk is secondary; the manifest is what the application reads first.
3All mutations are atomic: copy the file to a temp sibling, mutate the temp, reopen it once (HDF5 1.14.3 metadata-cache quirk), then rename over the original. A crash never leaves a half-written archive — at most a stale .tmp file beside it (see §8).
4Manifest version is gated. An unknown version in archive.json produces an explicit error; the application never guesses the layout.
5No host info: no hostnames, usernames, paths, or OS fingerprints. The archive records only application identity and timestamps.
6The pre-embedding file path of a source is never stored. Once a dataset is embedded, it has no link back to where it came from.
7Embedded workspace content is byte-identical to a standalone .h5 file. The same read/write helpers operate on the group handle as on a file root, so embedded sources behave exactly like standalone files.
8No images, opaque blobs, base64, executables, or scripts. The container stores only datasets, groups, and string metadata attributes — the same restriction as the single-dataset format.
9All numeric data is native HDF5 typed datasets (IEEE fp32/fp64, i32). Strings are VLEN UTF-8 (H5T_C_S1 + H5T_VARIABLE), shape (1,). Shapes are C order, row-major. The fp32/fp64 mix is inherited from the single-dataset format (uncorrected interferograms are fp32 on disk); cross-store-specific datasets (experiment results/) are fp64.
10Every mutation self-compacts the file. Because HDF5 does not reclaim bytes freed by H5Ldelete by default, the atomic copy step drops dead space and the archive stays near its live size instead of growing monotonically.

3. Container layout

The root holds one dataset (the manifest) and three optional group families. Groups are organized by function: embedded datasets, cross-workspace experiments, and batch recipes.

archive.json (vlen str) — §4, the manifest ├── sources/ embedded single-dataset workspaces │ ├── <id>/ (one per embedded dataset) │ │ │ @summary = "{id,name,memberCount,createdIso}" (JSON string) │ │ └── <workspace content — see Single-Dataset Spec> │ └── … ├── experiments/ cross-workspace analyses (optional) │ ├── <id>/ │ │ ├── config.json (vlen str) — §6.1 │ │ ├── fingerprint.json (vlen str) — §6.2 │ │ ├── results/ (fp64 datasets) — §6.3 │ │ │ ├── curve_0_x (fp64 [M]) │ │ │ ├── curve_0_ratio (fp64 [M]) │ │ │ └── … │ │ └── stats.json (vlen str) — §6.4 │ └── … └── recipes/ batch-processing recipes (optional) ├── <recipe-name> (vlen str, content = recipe JSON) — §7 └── …

4. archive.json manifest

Root-level VLEN-string dataset. JSON object. The single source of truth for the archive's contents. Written at creation, rewritten on every mutation that changes membership.

4.1 Schema

{
  "version": 2,
  "sources": [
    { "id": "sample_0001", "name": "sample_0001",
      "memberCount": 12, "createdIso": "2026-08-01T12:34:56Z" }
  ],
  "experiments": [
    { "id": "exp_0001", "name": "Absorbance 1",
      "type": "Absorbance", "createdIso": "2026-08-02T09:00:00Z" }
  ],
  "tabOrder": [ "ws:sample_0001", "exp:exp_0001", "ws:sample_0002" ]
}

4.2 Key reference

sources[].namestringDisplay name. May differ from id after a rename. The manifest name is authoritative; @summary mirrors it best-effort.

experiments[].typestring"Absorbance" or "Comparator".

4.3 Legacy tab-order fallbacks

Older archives may lack tabOrder. The reader then restores workspace tabs only (experiment tab order is empty, so persisted experiments load but do not auto-open as tabs):

  1. openTabs — array of source ids (legacy). Each id opens as a workspace tab.
  2. Per-source open boolean — sources with open = true open as workspace tabs, in manifest order.

If neither tabOrder nor openTabs is present and no source has open = true, no workspace tabs auto-open.

5. sources/<id>/ — embedded workspaces

One group per embedded dataset. The group name is the source id. The group's content is a complete single-dataset workspace, stored exactly as it would be in a standalone .h5 file.

sources/<id>/ @summary = "{\"id\":\"...\",\"name\":\"...\",\"memberCount\":N,\"createdIso\":\"...\"}" # --- workspace content (see Single-Dataset Spec) --- @format = "unified-spectral-data-container" @created = "2026-08-01T12:34:56Z" ├── workspace.json ├── measurement_config.json ├── measurement_comment.txt ├── tags ├── igm_uncorrected_x/ ├── igm_corrected_x/ ├── spectra/ ├── average_spectra/ ├── snr_spectra/ ├── allan_werle/ └── t100/

5.1 @summary attribute

JSON string attribute on each source group. Informational mirror of the manifest entry; the manifest is authoritative. Refreshed on save-back and rename.

KeyTypeDescription
idstringSource id (matches group name and manifest sources[].id)
namestringDisplay name (mirrors manifest)
memberCounti32Primary member count (mirrors manifest)
createdIsostringISO-8601 UTC timestamp

5.2 Inner layout

The group's children — root datasets, type groups, member datasets, and all @format/@created/@origin/@config/@schema attributes — are specified in full by the Single-Dataset Specification. An embedded source is read and written with the same helpers as a standalone file; the only difference is that the HDF5 root handle is the sources/<id> group rather than the file root.

Original-data immutability and inputs integrity (single-dataset rules 7, 10) apply inside each embedded source. Save-back rewrites the whole source group atomically.

6. experiments/<id>/ — cross-workspace analysis

One group per persisted experiment. Experiments overlay artifacts from one or more embedded datasets: Absorbance computes reference/sample ratios, Comparator overlays selected artifact types across datasets. Transient (unsaved) experiments have no group here; only persisted instances occupy space.

experiments/<id>/ ├── config.json (vlen str) — full instance state — §6.1 ├── fingerprint.json (vlen str) — per-source compute-time snapshots — §6.2 ├── results/ (fp64 datasets, Absorbance only) — §6.3 │ ├── curve_0_x (fp64 [M]) │ ├── curve_0_ratio (fp64 [M]) │ └── … └── stats.json (vlen str) — per-curve summary stats — §6.4

6.2 fingerprint.json

JSON string dataset. Per-source compute-time snapshots used to detect result staleness. Keyed by a composite string <sourceKey>\x1f<artifact>\x1f<memberId> (two curves may reference the same source with different members). On load, the application compares each snapshot to the source's current member state and raises a staleness flag on mismatch.

MemberSnapshot schema

KeyTypeDescription
memberIdstringResolved member id at compute time
dataHashuint64FNV-1a content hash over the member's x/y IEEE-754 bit patterns (stable across app versions)
effectiveParamsobjectNormalized params that determine content: active apodization window's field(s), zeroPadK, refLaserUm, xCorrectionMethod, prominence (peak-finding only). xUnit and sensitivity excluded (display-only).
validboolFalse for unresolvable members and legacy entries (dropped silently on load)
Staleness is data-grounded: a snapshot mismatch means the source's data or effective params changed since compute. The user sees a warning and a Recompute button; results are not auto-discarded.

6.3 results/

Group of fp64 datasets, Absorbance experiments only. One pair per computed curve. Comparator experiments store no results (they re-extract overlay curves live from the sources).

7. recipes/ — batch-processing recipes

Optional group. One VLEN-string dataset per recipe, named by the recipe name; the dataset content is the recipe JSON. Additive to the archive: recipe operations never touch archive.json, and the single-dataset validator is never run on cross files. Recipe names must be non-empty and contain no /.

7.3 Built-in recipes

Six built-in recipes are compiled into the application (Norton-Beer, K=2, Hilbert, no overrides, no Allan). They are in-memory defaults, not stored in the recipes/ group — the group holds only user-saved recipes. The UI lists built-ins first, then file-stored recipes appended after:

  • Average spectrum - NB weak/medium/strong (FWHM 1.2 / 1.4 / 1.6) — artifacts: spectra, average.
  • All - NB weak/medium/strong — adds snr + t100 (ASTM E1421 bands).

8. Atomicity & versioning

8.1 Atomic mutation contract

Every write — embed, remove, rename, save-back, experiment write/remove, recipe write/remove, tab-order save — follows the same atomic window:

1. Copy path → path.tmp          (object-by-object H5Ocopy; drops dead space)
2. Mutate path.tmp               (the actual write)
3. Reopen path.tmp RDONLY        (HDF5 1.14.3 metadata-cache finalize quirk)
4. Rename path.tmp → path        (delete-then-rename fallback on Windows)

A crash at any step leaves the original intact and at most a stale .tmp beside it. The temp is removed at the start of the next mutation.

8.2 Compaction-on-save

HDF5 does not reclaim bytes freed by H5Ldelete by default (its free-space manager does not track that space). The atomic copy step copies only live objects, so deleted-and-recreated members do not accumulate dead bytes. The archive self-compacts to near its live size on every mutation instead of growing monotonically.

8.3 Version gate

The manifest version field is checked on every open. The current version is 2. An unknown version produces an explicit error ("unsupported archive version N (expected 2)") — the application never guesses the layout of a newer or older archive.

8.4 Save-back semantics

Saving an embedded workspace rewrites the whole sources/<id>/ group atomically (delete + recreate within the temp copy). Original-data immutability is enforced against the current on-disk group; a fresh embed (missing group) skips the check. The manifest entry's memberCount and name are refreshed in the same save, and @summary is rewritten to match.

9. File-type discrimination

The application must tell a multi-workspace .cross.h5 from a single-dataset .h5 before attempting to open it, because the two have different root layouts:

File typeExtensionRoot discriminatorOpen path
Single-dataset.h5Root @format = "unified-spectral-data-container"H5Store::load
Multi-workspace.cross.h5Root dataset archive.json exists; no root @formatcrossLoad
The cross file deliberately has no root @format attribute. H5Store::load rejects any file missing @format, so the generic open path (openWorkspaceInNewTab) sniffs for archive.json and routes cross files to crossLoad before that check can fire. Paths that already know a file is a cross archive (recent-cross list, session tab) call crossOpenProject directly.
