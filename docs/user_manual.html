FTS Data Explorer

User manual  |  Applies to version 26.08 and later  |  2026-09-26

FTS Data Explorer is a multiplatform desktop application for processing and exploring raw data from FTIR spectrometers. It is designed to work as fast as possible and be the one-stop shop for extracting useful insights from massive datasets produced in a lab. The application does not support any particular spectrometer but is aimed mostly at DIY instruments. Full processing chain is supported, from raw voltages recorded from detectors to absorbance plots and data comparison. Incompatible data sources are loaded using standardized data adapters written in Python. The user is free to add new adapters without the need to modify the application binary itself.

Chapter 1 - Introduction

1. Overview

FTS Data Explorer is a desktop application for analysis of Fourier-transform spectrometer data: it takes raw measurements in, turns them into spectra, runs the standard analyses, and keeps the results together in a single h5 file. It works with files from lab-built and commercial instruments and it is meant for day-to-day laboratory work. Fast check for odd measurements, finding the optimal processing setting, preparing a series of scans for averaging, or investigating how stable an instrument is over time. All without writing a new script for every question. The application does not acquire data directly from the instrument - all measurements must arrive as h5 files.

Everything is organized around one container, the workspace. A workspace is a single HDF5 (.h5) file that holds the measurements, their metadata and comments, the processing settings, the computed results, and - for multi-dataset work - experiments and batch recipes. Data produced by other software (vendor CSVs, text dumps, exported spectra) enters through the built-in Conversion screen, which runs small converter scripts (in Python) and writes a compliant workspace file (Section 6). Because the workspace records the complete state of the work, reopening it restores the session exactly as it was left; Section 4 explains what is stored where.

What you can do with it:

  • Inspect measurements. Overlay up to five interferograms or spectra, zoom and pan them, and read exact values with the tracking cursor (Sections 8–10).
  • Compute spectra. Correct the X axis with the Hilbert transform or peak finding, choose an apodization window and zero-padding, and display the result in cm⁻¹, µm, or THz (Sections 7 and 11).
  • Run the standard analyses. Average spectrum, spectral SNR, 100% transmittance with ASTM E1421-compliant or custom energy ratios, and Allan variance for stability assesment (Sections 12–15).
  • Compare datasets. Comparator experiment can overlay all types of artifacts calculated from several datasets and compute difference curves.
  • Calculate absorbance/transmittance spectra of samples. Absorbance experiment allows to freely select reference and sample spectra from any available dataset and overlay curves from multiple experiments. Residual calculation is supported.
  • Check spectral features. Mark HITRAN band markers for eight common gases on the Spectrum View and Average plots (and in spectral experiment viewers) (Section 16).
  • Export and archive. Write any computed curve to CSV and save the complete state back into the h5 workspace (Section 17).

The application runs locally and ships as a single executable for Linux and Windows. No installation required. The Windows build is fully static; the Linux build uses the system OpenGL and X11 libraries. Calculations are multithreaded, and the worker count is configurable in the Settings menu to adjust the system load.

If you are opening the application for the first time, continue with Section 2 (Workflow) and Section 3 (Welcome screen). If you already have a workspace file, Section 6.2 explains how to open it, and Section 8 covers the file list.

2. Workflow

The application is built around a simple workflow: raw measurements come in, processing settings are tuned by hand on one dataset, and the same method is applied to the remaining datasets using the batch processing feature. Finally, outputs are analyzed or exported and the workspace, with all its settings and calculation results, is saved back to the h5 file.

  1. Convert the raw data. Measurements are read from the application's HDF5 workspace format. Files from other sources are converted by a converter script on the Conversion screen. See Section 6.
  2. Load the workspace. Open the file in a tab; its measurements, metadata, and saved settings are restored with it.
  3. Tune the processing. Work on one dataset manually - X-axis correction, apodization, zero-padding, axis ranges - until the spectra look right. See Sections 7, 10, and 11.
  4. Replicate the method. Capture the settings that worked into a batch recipe and apply it to the other datasets, so that every file is processed the same way. See Section 19.
  5. Extract the information. Use the analysis panels (average spectrum, SNR, 100% transmittance with energy ratios, Allan variance) and the cross-dataset experiments. See Sections 12–15 and 20–22.
  6. Export the results. Write any curve, spectrum, or table to CSV for reports and further analysis. See Section 17.
  7. Save the workspace. The complete state - inputs, settings, comments, results, experiments - is stored back into a single .h5 file for later access, archiving, or sharing.

Settings can be changed and results recomputed at any time. Because the workspace file records the whole state of an analysis, it can be reopened later, on this or another machine, and continued where it was left.

4. Workspace files and data storage

Everything the application produces is stored in HDF5 files - a binary, self-describing container format widely used in scientific computing. It uses two different kinds of file storage that share the .h5 extension: a single-dataset workspace and a multi-workspace container (Section 18). The application tells the two apart by their content, not by the file name, so both open the same way - from the Welcome screen or File → Open Workspace (.h5).

4.1 What a workspace file contains

A workspace holds more than the measurements. It records the complete state of the work done on them, which is why a reopened dataset looks exactly as it was left:

  • Measurements - raw interferograms (reference and primary) or precomputed spectra, and their timestamps.
  • Metadata - the measurement configuration stored with the data, plus the comment and tags edited in the Metadata panel (Section 9).
  • Processing settings and display state - X-axis correction, reference laser wavelength, apodization, zero-padding, detector sensitivity, axis units, plot zoom ranges, and the file selection.
  • Computed results - spectra, average spectrum, SNR, 100% T, Allan variance, and the inputs they were calculated from.
  • Experiments and recipes - Comparator and Absorbance setups with their saved results, and batch-processing recipes; these live in multi-workspace files.

4.2 Originals and derivatives

Everything in a workspace falls into one of two kinds. Originals are the measurements themselves: the interferograms or precomputed spectra created by an instrument. Derivatives are everything computed from them - spectra, average spectrum, SNR, 100% T, and Allan variance. The two kinds are treated differently:

  • Originals are never removed automatically. Deleting one always asks for confirmation, and any result calculated from it is marked stale (Section 8).
  • Derivatives can be removed at any time, because they can always be recomputed. Strip derivatives in the Files panel clears all of them at once (Section 4.3).

When the inputs of a stored result change, the panel that displays it shows a Stale data: source changed. overlay with a Recompute button. How a save treats a stale result depends on the path:

  • Save (Ctrl+S) keeps it in the file as it is.
  • Save As, and the save when closing a tab, drop stale results after a “Stale Data Will Be Dropped” confirmation.
  • The exit Save All drops them without asking.

4.3 Stripping derivatives

Strip derivatives at the top of the Files panel removes every computed result from the workspace in one action - spectra, average spectrum, SNR, 100% T, and Allan variance - leaving only the measurements. This is the way to return a workspace to its raw state before a new round of processing, or before sharing or archiving. Stripped workspaces take less disk space.

4.4 Archiving and sharing

Because a workspace is one self-contained file, archiving or sending a dataset is a matter of copying that file. The format is open and documented - see the single-dataset specification and the multi-workspace specification - so the data remains readable with generic HDF5 tools even where the application is not available. Multi-workspace files embed complete copies of their datasets (Section 18), which costs disk space but keeps experiments intact when source files are moved, renamed, or deleted.

Saving writes the file atomically, so an interrupted save leaves the previous version intact.

6. Getting data in

Opening an existing HDF5 workspace

Use File → Open Workspace (.h5), a recent entry, or the Open .h5 button on the Welcome screen. Files with the .h5 extension are opened as workspaces; if the file contains a multi-workspace archive, it opens in the Session tab instead. Opening a file that is already open just activates its tab.

Converting non-HDF5 data

Data that is not already in the h5 workspace format is converted with a converter script written in Python. If the converter follows the standard described in Section 26, then it can be invoked from this window. The Conversion screen is opened from the Welcome screen (Convert Dataset) or from the menu (File → Convert Dataset...).

Setup

The Setup group configures where converters come from and which Python to use:

  • Converter repo URL - location of the standard converter collection. Defaults to the official GitHub repository.
  • Converter repo local destination - where the collection is stored locally. Browse... picks a folder.
  • Update converters base - clones the repository the first time, then pulls updates. Needs git; the detected version is shown below the button.
  • Python interpreter - interpreter used to run scripts, with a Browse... button and a Test button. The detected Python and h5py versions are shown below the row when the probe succeeds.

Banners at the top of the window report missing dependencies: without git updating is disabled, without Python or the h5py/numpy packages conversion is disabled. The Refresh button only rescans installed converters - it does not use the network. When a clone already exists, it is updated automatically at startup. The automated Git repository handling is there for convenience but not required. The Converter window can accept any directory containing converter scripts instead of a repo.

Running a conversion

  1. Select a converter from the list. Its description, expected input, and a format documentation will appear in the input format panel.
  2. Set the Input path. Converters that expect a single file open a file dialog, converters that take a directory open a folder dialog instead.
  3. Set the Output directory. The output file name is derived from the input name (<name>.h5).
  4. Click Convert, or Convert and open to open the result in a workspace tab as soon as it is written.

The Log pane shows the last lines of converter output. If the conversion fails, the reason is shown in the banner area, for example Converter exited with code N or Converted file failed validation: .... Press Exit when you are done.

7. Spectrum calculation

A spectrum is computed from the primary detector trace in a fixed sequence of stages. The chain below shows the complete data flow; every stage runs in order, and the user-facing stages are configured from the Interferogram and Spectrum panels (Sections 10 and 11).

Not every dataset runs the whole chain. A dataset with an already corrected axis skips the X-axis correction stage and uses its stored OPD axis. A dataset that contains precomputed spectra skips the whole process.

Spectra are recalculated in real time as settings change, so the chain can be tuned interactively while watching the result (Section 11).

8. Files panel

The Files panel lists the measurements in the current dataset. The header shows the dataset name, followed by selection helpers:

  • Select: All | None | 10 | 50% - set the checkbox (batch selection) for all files, none, the first ten, or the first half of the list.
  • Strip derivatives - removes every computed result from the workspace (spectra, average, SNR, Allan, 100% T).

Each row contains a delete button (×), the file name, and a checkbox. Row backgrounds match the plot colours of the currently displayed files. The colours are assigned in the order the files are selected.

8.1 Selecting records

  • Click a file to load it on its own, replacing the current selection.
  • Ctrl+click toggles the file in or out of a multi-file selection (up to 5 files).
  • Shift+click selects a range of files.

The checkboxes on the right are separate from the highlighted selection. They choose the files used by the batch analyses (Average, SNR, Allan, 100% T standard deviation) and by the Spectra from selected files export. All files are checked when a workspace is opened for the first time.

8.2 Deleting records

Clicking × (or pressing Delete) asks for confirmation in a Delete member? dialog that shows the workspace path of the entry (for example /igm_uncorrected_x/record_0). If other results depend on the file, the dialog notes that they may become stale. Deletion is written to the file only when you save the workspace.

10. Interferogram panel

The view stacks two plots with a shared X axis: the reference detector on top (when the dataset has one) and the primary detector below. The X axis shows the sample number or the optical path difference (OPD [µm]), and Y shows detector voltage. All records selected in the Files panel are overlaid for easy comparison. The apodization window selected in the Spectrum panel is drawn as a cyan overlay on the primary plot.

10.1 Interacting with the plots

  • Mouse wheel - zoom. In the interferogram and spectral plots only X is affected (Y is auto-fitted).
  • Shift+drag - hold Shift and drag to mark an X range. When you release Shift, both plots zoom to it.
  • ESC - reset the zoom.
  • ← / → - pan by 10% of the visible range.

The same controls work in every plot panel (Spectrum, Average, SNR, Allan slice, 100% T, experiment viewers).

10.2 Large datasets

When the first loaded file has more than 50 000 samples in a detector, the corresponding interferogram plot switches to large-data mode: the primary plot is annotated LARGE DATA, ImPlot's built-in mouse interactions (wheel, pan, box-select) are disabled - the tracking cursor and Shift+drag range selection still respond, and keyboard panning and ESC still work - and anti-aliasing is switched off. With downsampling enabled (the default), long records are decimated for display and stay fully interactive. Spectra and OPD calculations always use the underlying full-resolution data for calculations. Downsampling is display-only.

12. Average spectrum

The Average panel computes the mean spectrum of all files ticked in the Files panel (at least one). Press Calculate average. A progress bar shows the state, and the plot is labelled Average of N. The plot controls are Cursor, Y scale (lin/log/dB), X unit, Match X to Spectrum View (copies the Spectrum panel's unit and zoom range), and Y Axis with the usual all/tight/force modes. The result is stored in the workspace and used as a reference option by the 100% T and Absorbance panels.

If the checked files or the processing settings change after a calculation, the plot shows a Stale data: source changed. overlay with a Recompute button. Hovering it lists what changed (up to four sources).

13. SNR

The SNR panel combines repeat measurements into a per-wavelength signal-to-noise ratio: the mean spectrum divided by the sample standard deviation across files. At least two files must be ticked in the Files panel. The header shows how many are selected. Press Calculate SNR to compute. The Y scale offers lin and log (no dB). The remaining controls match the Average panel. The result is labelled SNR of N.

14. Allan variance

The Allan panel estimates the Allan-Werle variance as a function of integration time (τ), either from each file's transmittance against the mean of the selected spectra (Calc base = 100% T) or from the raw spectra (Calc base = Spectrum). Integration time is replaced with the number of measurements to maximize compatibility of the application across differing timestamp standards (or the lack of timestamps). It is up to the user to export the data and replace X axis with seconds, if required. It needs at least two ticked files. The result is a 3D surface plus a 2D slice. Rotate, zoom and pan the surface with the mouse. The slice for the selected wavelength is drawn as a white curve on the surface and as a separate log-log plot below it.

15. 100% Transmission line

The 100% T panel divides each sample spectrum by a reference spectrum and plots the result as transmittance in percent, together with an optional standard-deviation curve and ASTM E1421-style energy ratios. The transmittance curves are drawn for the files highlighted in the Files panel (up to five). The standard deviation is computed over the files ticked with checkboxes (at least two).

15.1 Reference spectrum

Choose the reference spectrum source with File, CSV, or Avg:

  • File - press Set as reference to use the spectrum of the first highlighted file.
  • CSV - type or browse to a two-column CSV file and press Load. The unit is taken from the file header when recognisable.
  • Avg - press Use average to use the computed average spectrum. Disabled until an average exists.
A reference CSV starts with a header line, followed by rows of two comma-separated numeric columns: x, then y. The header selects the x unit - it must contain the word Wavenumber (cm⁻¹), Wavelength (µm), or Frequency (THz); anything else is read as cm⁻¹. The x values are converted to the unit selected in the Spectrum panel. Empty and non-numeric rows are skipped.

15.2 Energy ratios

Three ratio rows A, B, C each take a numerator and a denominator band in cm⁻¹. ASTM E1421 fills the standard bands (4000/2000, 2000/1000, 150/max). max is recognized as valid and means the point of the maximum spectral brightness. The table below the plots lists every highlighted file and, once a standard deviation has been computed, adds Average, Spread (max - min), and Std Dev rows.

15.3 Standard deviation

Calculate std computes the sample standard deviation across all ticked files (at least two) and adds a second, X-linked plot with the Std Dev T(%) curve. Energy ratio statistics are available only when Std Dev T(%) is calculated.

Bins where the reference spectrum is close to zero relative to its peak are masked, so the transmittance is not divided by numerical noise.

The markers appear on the Spectrum View and Average plots (and in spectral experiment viewers). They are display-only and never appear in exports. This is not meant to be a precision feature - it is there to help quickly distinguish noise from popular gas contaminants.

Chapter 3 - Multi-dataset work

18. Multi-workspace sessions

A multi-workspace is a single .h5 file that contains several complete datasets plus any experiments and batch recipes bundled with them. Because every used dataset is copied in full, the archive carries all measurement data with it. The original measurement files can be gone and the embedded datasets will still open. The .h5 layout of this multi-workspace archive is documented in the multi-workspace format specification. The user does not need to know whether an .h5 file is a single-dataset or a multi-workspace - the application will distinguish them automatically and open correctly.

Whenever an .h5 is opened, the primary interface is presented to the user. Each workspace, for either a dataset or an experiment, opens in its own tab. A Session tab is always open and located on the left side of the tab ribbon. 19. Batch processing

Batch processing is available in multi-workspace sessions, in the Batch Processing panel of the Session tab. It applies the same processing recipe to any number of embedded datasets. Existing derived results are replaced with the new ones, as specified by the selected recipe.

19.1 Recipes

A recipe holds the spectrum processing settings (zero-padding, apodization window and its parameter, X-correction method and peak prominence), optional overrides for the reference laser wavelength and detector sensitivity, the list of artifacts to produce (spectra, average, SNR, 100% T, Allan), energy ratios, and the Allan decimation and wavelength range. RecipeProduces

24. Single-dataset workspace format

This page is the reference specification for the single-dataset workspace format. Read it if you plan to write a converter (Section 26) or to read workspace files with your own tools.

HDF5 unified spectral data container  |  Specification v.1  |  2026-08-02

24.1 Overview

One HDF5 file holds the entire workspace: raw measurements, computed artifacts, and per-panel data-view settings.

24.1.1 Format rules

#Rule
1Every member - interferogram dataset or member group - carries a kind attribute: "original" (as loaded) or "derivative" (computed). kind = "original" is written once, never overwritten.
2Every group carries @origin and @config attributes (JSON strings). Numeric data lives in datasets; attributes are metadata only.
3No file versioning. A static root @format attribute identifies the layout.
4No host info: no hostnames, usernames, paths, or OS fingerprints. @origin records only application identity and timestamp.
5No images, opaque blobs, base64, executables, or scripts. The container stores only datasets, groups, and string metadata attributes.
6All numeric data is native HDF5 typed datasets (IEEE fp32/fp64, i32). Datatype is the format specifier; @config records units. Strings: VLEN UTF-8 (H5T_C_S1 + H5T_VARIABLE), shape (1,). Shapes: C order, row-major. All 2-column datasets carry columns and units string attributes.
7Derivative members can be safely stripped: delete any group or dataset with kind = "derivative". Original members - interferograms with kind = "original" and original spectra - are untouched. Apps must tolerate stripped files and recompute on demand.
8Root datasets: workspace.json (§24.8), measurement_config.json (§24.6.1), measurement_comment.txt (§24.6.2), tags (§24.6.3). All may be empty.
9Configuration is extensible: unknown keys are preserved verbatim on save.
10Derivative datasets reference their source data via inputs (absolute HDF5 paths in @config). Every referenced path must exist in the file - a saved file must never contain an inputs entry pointing to a deleted member.

24.2 Container layout

Groups are organized by data type. All x/y-style data is stored as 2-column datasets with columns and units attributes. Original measurements may carry a timestamp attribute.

24.2.3 Interferograms

All interferograms are flat 2D datasets directly inside the type group. No per-scan sub-groups; @origin/@config are pool-level attributes on the group. Each original dataset may carry a timestamp attribute (ISO-8601 UTC).

24.2.3.1 Uncorrected IFG - igm_uncorrected_x/
igm_uncorrected_x/ attrs: origin, config record_0 (fp32/fp64 [N,2]) attrs["kind"] = "original" attrs["columns"] = ["Reference detector", "Primary detector"] attrs["units"] = ["V", "V"]

No OPD axis - x-axis is sample indices. axisCorrected is false. Imported from WUST Mini FTS CSV raw measurements.

24.2.3.2 Corrected IFG - igm_corrected_x/
igm_corrected_x/ attrs: origin, config record_0 (fp64 [N,2]) attrs["kind"] = "original" | "derivative" attrs["columns"] = ["Primary detector", "OPD axis"] attrs["units"] = ["V", "um"]

axisCorrected is true. Corrected single IFGs are imported from ArcOptix IGMs TXT measurements (kind = "original"). Derivative corrected IFGs may be produced by computation pipelines (e.g. phase correction).

24.2.4 Spectrum member groups

Precomputed spectra (kind = "original") come from measurement sources. FFT-computed spectra (kind = "derivative") come from the app pipeline (§24.7.3). Both use the same layout:

spectra/<id>/ (member group) attrs: kind, origin, config data (fp64 [M,2]) attrs["columns"] = ["x", "y"] attrs["units"] = ["cm-1", "V"]

Column 0: x-axis (wavenumber, wavelength, or THz per @config xUnit). Column 1: spectrum magnitude. Units from @config xUnit and yUnits.

24.2.5 Derivative member groups

24.2.5.1 Average spectrum (average_spectra/)

Mean spectrum computed from N input interferograms. Same layout as §24.2.4: data (fp64 [M,2]) with columns ["x", "y"].

24.2.5.2 SNR spectrum (snr_spectra/)

Signal-to-noise ratio per wavelength bin, computed from ≥ 2 input interferograms. SNR = mean / standard deviation, calculated online across input files.

snr_spectra/<id>/ (member group) attrs: kind, origin, config data (fp64 [M,2]) attrs["columns"] = ["x", "y"] attrs["units"] = ["cm-1", ""]
24.2.5.3 Allan-Werle plot (allan_werle/)

Allan-Werle variance as a function of averaging window (taus, in measurements) and wavelength - it characterises instrument stability.

allan_werle/<id>/ (member group) attrs: kind, origin, config surface_data (fp64 [T,W]) attrs["columns"] = ["taus", "wavelengths", "allan_var"] wavelengths (fp64 [W]) attrs["units"] = "um" taus (fp64 [T]) attrs["units"] = "measurements"

surface_data is a T × W array (cluster sizes × wavelength bins). The columns attribute labels its three axes as ["taus", "wavelengths", "allan_var"]; wavelengths holds the wavelength axis in µm and taus holds the cluster sizes in measurements.

24.2.5.4 100% T curves (t100/)

Transmittance analysis: T% = (sample spectrum / reference spectrum) × 100 for each input file.

t100/<id>/ (member group) attrs: kind, origin, config reference (fp64 [M,2]) attrs["columns"] = ["x", "y"] attrs["units"] = ["cm-1", "a.u."] stddev (fp64 [M,2]) attrs["columns"] = ["x", "y"] attrs["units"] = ["cm-1", "%"] transmittance/<file_id>/ data (fp64 [M,2]) attrs["columns"] = ["x", "T%"] attrs["units"] = ["cm-1", "%"]

reference: reference spectrum (file or average). stddev: standard deviation of T% across all checked files at each x. transmittance/<file_id>/: one subgroup per input file.

24.3 Member IDs & references

  • <id> is a human-readable slug (sanitized source basename, e.g. sample_0001), unique within its type group, stable across saves.
  • On collision, append a numeric suffix (sample_0001_2).
  • Derivative IDs are fixed per artifact type: spec_<ifgId> for computed spectra, average, snr, allan, and t100.
  • inputs in @config reference members by absolute HDF5 path: ["/igm_uncorrected_x/record_0"].

25.1 Overview

A multi-workspace container (a .h5 file, distinguished from a single-dataset .h5 by its root archive.json - see §25.9) holds many single-dataset workspaces plus the cross-workspace artifacts built on top of them. It is the project file the application opens when a user works with several datasets at once.

Each embedded workspace is a complete unified-spectral-data-container - raw measurements, computed spectra, and per-panel view state - stored byte-identically under a sources/<id>/ group. The container adds three things the single-dataset format does not have:

  • An archive manifest (archive.json) that is the single source of truth for what the archive contains.
  • Cross-workspace experiments (experiments/<id>/) - Absorbance and Comparator analyses that overlay artifacts from one or more embedded datasets.
  • Batch-processing recipes (recipes/) - reusable processing parameter sets that can be applied across datasets.

The inner layout of each embedded workspace is specified by the Single-Dataset Specification; this document does not repeat it.

25.2 Format rules

#Rule
1The container has no root @format attribute. This distinguishes it from a single-dataset .h5, which always carries @format = "unified-spectral-data-container". The archive.json dataset at the root is the discriminator (see §25.9).
2archive.json is the source of truth. The list of sources, experiments, and the tab-strip order live in the manifest. Group existence on disk is secondary; the manifest is what the application reads first.
3All mutations are atomic: copy the file to a temp sibling, mutate the temp, reopen it once (HDF5 1.14.3 metadata-cache quirk), then rename over the original. A crash never leaves a half-written archive - at most a stale .tmp file beside it (see §25.8).
4Manifest version is gated. An unknown version in archive.json produces an explicit error; the application never guesses the layout.
5No host info: no hostnames, usernames, paths, or OS fingerprints. The archive records only application identity and timestamps.
6The pre-embedding file path of a source is never stored. Once a dataset is embedded, it has no link back to where it came from.
7Embedded workspace content is byte-identical to a standalone .h5 file. The same read/write helpers operate on the group handle as on a file root, so embedded sources behave exactly like standalone files.
8No images, opaque blobs, base64, executables, or scripts. The container stores only datasets, groups, and string metadata attributes - the same restriction as the single-dataset format.
9All numeric data is native HDF5 typed datasets (IEEE fp32/fp64, i32). Strings are VLEN UTF-8 (H5T_C_S1 + H5T_VARIABLE), shape (1,). Shapes are C order, row-major. The fp32/fp64 mix is inherited from the single-dataset format (uncorrected interferograms are fp32 on disk); multi-workspace-specific datasets (experiment results/) are fp64.
10Every mutation self-compacts the file. Because HDF5 does not reclaim bytes freed by H5Ldelete by default, the atomic copy step drops dead space and the archive stays near its live size instead of growing monotonically.

25.5 sources/<id>/ - embedded workspaces

One group per embedded dataset. The group name is the source id. The group's content is a complete single-dataset workspace, stored exactly as it would be in a standalone .h5 file.

JSON string attribute on each source group. Informational mirror of the manifest entry; the manifest is authoritative. Name and member count are refreshed on save-back and rename; createdIso is rewritten with the current time on save-back.

25.5.2 Inner layout

The group's children - root datasets, type groups, member datasets, and all @format/@created/@origin/@config/@schema attributes - are specified in full by the Single-Dataset Specification. An embedded source is read and written with the same helpers as a standalone file; the only difference is that the HDF5 root handle is the sources/<id> group rather than the file root.

Original-data immutability and inputs integrity (single-dataset rules 7, 10) apply inside each embedded source. Save-back rewrites the whole source group atomically.

25.6 experiments/<id>/ - cross-workspace analysis

One group per persisted experiment. Experiments overlay artifacts from one or more embedded datasets: Absorbance computes reference/sample ratios, Comparator overlays selected artifact types across datasets. Transient (unsaved) experiments have no group here; only persisted instances occupy space.

Six built-in recipes are compiled into the application (Norton-Beer, K=2, Hilbert, no overrides, no Allan). They are in-memory defaults, not stored in the recipes/ group - the group holds only user-saved recipes. The UI lists built-ins first, then file-stored recipes appended after:

  • All - NB weak/medium/strong - adds snr + t100 (ASTM E1421 bands).

25.8 Atomicity & versioning

25.8.1 Atomic mutation contract

Every write - embed, remove, rename, save-back, experiment write/remove, recipe write/remove, tab-order save - follows the same atomic window:

1. Copy path → path.tmp          (object-by-object H5Ocopy; drops dead space)
2. Mutate path.tmp               (the actual write)
3. Reopen path.tmp RDONLY        (HDF5 1.14.3 metadata-cache finalize quirk)
4. Rename path.tmp → path        (delete-then-rename fallback on Windows)

A crash at any step leaves the original intact and at most a stale .tmp beside it. The temp is removed at the start of the next mutation.

25.8.2 Compaction-on-save

HDF5 does not reclaim bytes freed by H5Ldelete by default (its free-space manager does not track that space). The atomic copy step copies only live objects, so deleted-and-recreated members do not accumulate dead bytes. The archive self-compacts to near its live size on every mutation instead of growing monotonically.

25.8.3 Version gate

The manifest version field is checked on every open. The current version is 2. An unknown version produces an explicit error ("unsupported archive version N (expected 2)") - the application never guesses the layout of a newer or older archive.

25.8.4 Save-back semantics

Saving an embedded workspace rewrites the whole sources/<id>/ group atomically (delete + recreate within the temp copy). Original-data immutability is enforced against the current on-disk group; a fresh embed (missing group) skips the check. The manifest entry's memberCount and name are refreshed in the same save, and @summary is rewritten to match.

25.9 File-type discrimination

The application must tell a multi-workspace .h5 from a single-dataset .h5 before attempting to open it, because the two have different root layouts:

File typeExtensionRoot discriminatorOpen path
Single-dataset.h5Root @format = "unified-spectral-data-container"H5Store::load
Multi-workspace.h5Root dataset archive.json exists; no root @formatmultiWorkspaceLoad
The multi-workspace file deliberately has no root @format attribute. H5Store::load rejects any file missing @format, so the generic open path (openWorkspaceInNewTab) sniffs for archive.json and routes multi-workspace files to multiWorkspaceLoad before that check can fire. Paths that already know a file is a multi-workspace archive (recent multi-workspace list, session tab) call multiWorkspaceOpenProject directly.

25.10 Reading the manifest with h5py

The manifest is a variable-length string dataset, so opening a multi-workspace file starts by reading and parsing it: 

import h5py
import json

with h5py.File("comparison.h5", "r") as f:
    if "archive.json" not in f:
        raise SystemExit("not a multi-workspace container")

    manifest = json.loads(f["archive.json"].asstr()[0])
    print("version:", manifest["version"])
    for source in manifest["sources"]:
        print(source["id"], source["name"], source["memberCount"])

26. Writing a data converter

Converters are small stand-alone Python scripts that turn an arbitrary measurement format into the workspace format described in Section 24. They are the only directly supported way to bring foreign data into the application - the application itself does not parse vendor formats. The Conversion screen (Section 6.3) runs them, and the headless -c command (Section 27) runs the same scripts from a terminal.

26.1 How converters are discovered

Installed converters are collected from a single place: the converter repository directory - the local clone of the standard collection created by the Update converters base button (Section 6). The directory does not have to be a git clone: any folder of converter scripts can be set as the Converter repo local destination.

Only regular .py files directly inside the directory are considered. Each file is identified by the manifest at its top; a script whose manifest is missing or unparsable is never executed; it is listed with the parse error. If two scripts declare the same id, the first one in alphabetical order wins. Changes on disk are picked up by pressing Refresh on the Conversion screen.

26.2 The converter contract

<python> <script> <input> <output.h5> [--param value ...]
  • <input> is a file or a directory, as declared in the manifest.
  • <output.h5> is the file the script must create: a single-dataset workspace (Section 24) that passes validation.
  • Write atomically - build the file under a temporary name and rename it into place when it is complete. An interrupted conversion must never leave a half-written .h5 behind.
  • Exit with status 0 on success. Any other exit status aborts the conversion; the last lines of the script's output are shown in the Conversion screen's log pane.

26.3 The manifest

The first lines of the script describe it to the application. They are plain text, not Python, and must start with #: 

#!/usr/bin/env python3
#FTS_CONVERTER {"id":"my_instrument_csv","name":"My Instrument CSV","version":"1.0",
#  "description":"Import one CSV export per scan",
#  "input":"directory","extensions":[".csv"]}
#FTS_FORMAT
# First line: "Reference [V],Primary [V]".
# Each following line is one sample pair. One file per scan inside the directory.
#FTS_FORMAT_END
#FTS_FORMAT_SAMPLE
# Reference [V],Primary [V]
# -0.00123,0.00084
# 0.00031,-0.00047
#FTS_FORMAT_SAMPLE_END
FieldMeaning
idRequired. Unique among all converters; also the name used by the headless -c flag.
nameDisplay name (defaults to the id).

descriptionOne-line description shown in the converter list.

The #FTS_FORMAT block is the prose shown in the Input format pane; #FTS_FORMAT_SAMPLE is a verbatim sample with the leading # stripped.

26.4 Writing the workspace file

The smallest useful converter writes the four root datasets, then one interferogram group. The application runs every converter as <python> <script> <input> <output.h5>, so the skeleton ends with an entry point - only parse_input, which turns the instrument's files into scan arrays, is left to implement. It is adapted from the WUST converter shipped with the standard collection: 

import datetime
import json
import os

import h5py
import numpy as np

SPEC_ATTR = "unified-spectral-data-container"


def utc_now():
    return datetime.datetime.now(datetime.timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")


def write_vlen_str(group, name, text):
    """Variable-length UTF-8 string dataset (shape (1,))."""
    dt = h5py.special_dtype(vlen=str)
    group.create_dataset(name, data=np.array([text], dtype=object), dtype=dt)


def write_container(out_path, scans):
    """scans: [(name, ndarray[N, 2] fp32), ...]"""
    tmp_path = out_path + ".tmp"
    with h5py.File(tmp_path, "w") as f:
        f.attrs["format"] = SPEC_ATTR
        f.attrs["created"] = utc_now()

        write_vlen_str(f, "workspace.json", "{}")
        write_vlen_str(f, "measurement_config.json", json.dumps({}))
        write_vlen_str(f, "measurement_comment.txt", "")
        write_vlen_str(f, "tags", "")

        group = f.create_group("igm_uncorrected_x")
        group.attrs["origin"] = json.dumps({
            "timestamp": utc_now(),
            "application": "my_instrument_csv",
            "version": "1.0",
        })
        for name, arr in scans:
            ds = group.create_dataset(name, data=arr.astype(np.float32))
            ds.attrs["kind"] = "original"
            ds.attrs["columns"] = ["Reference detector", "Primary detector"]
            ds.attrs["units"] = ["V", "V"]
        group.attrs["config"] = json.dumps({
            "sourceFormat": "csv",
            "dataType": "igm_uncorrected_x",
            "axisCorrected": False,
            "detectorUnits": "V",
            "opdUnits": "um",
            "channelOrder": ["Reference detector", "Primary detector"],
            "fileCount": len(scans),
            "pointsPerFile": int(scans[0][1].shape[0]) if scans else 0,
        })

    os.replace(tmp_path, out_path)   # atomic: no half-written file is ever visible


def parse_input(input_path):
    """Parse the instrument's format into [(name, ndarray[N, 2] fp32), ...]."""
    raise NotImplementedError("replace this with your format's parsing")


def main():
    import sys
    if len(sys.argv) != 3:
        raise SystemExit("usage: my_instrument_csv.py <input> <output.h5>")
    scans = parse_input(sys.argv[1])
    write_container(sys.argv[2], scans)


if __name__ == "__main__":
    main()

Points to keep in mind when adapting this skeleton:

  • For spectra, x/y datasets are two-column with the x axis in column 0. Interferogram groups are special: uncorrected is [Reference detector, Primary detector], corrected is [Primary detector, OPD axis].
  • Every dataset carries kind = "original" plus columns and units string attributes.
  • Every group carries @origin and @config JSON attributes. The application stores them verbatim - dataset type and axis handling come from which group the members live in, not from @config - but keep the keys shown above for external tools and round-tripping.
  • Data with an OPD axis belongs in igm_corrected_x/ with axisCorrected: true and columns ["Primary detector", "OPD axis"]. Converters that deliver spectra directly write original members under spectra/.
  • All strings are variable-length UTF-8 - use the helper shown above rather than fixed width arrays.

26.5 Testing a converter

  1. Run the script by hand exactly as the application would: python3 my_instrument_csv.py <input> /tmp/out.h5. A non-zero exit status aborts the conversion in the application as well.
  2. Run it through the application's own path to check validation and logging: fts_data_explorer -c my_instrument_csv <input> out.h5 (Section 27). Use -l converter to see whether the manifest was parsed.
  3. Inspect the result with any HDF5 tool, for example: 
    python3 - <<'PY'
import h5py

with h5py.File("out.h5", "r") as f:
    print(dict(f.attrs))
    print(list(f["igm_uncorrected_x"].keys()))
PY
  4. Open the file in the application and check the Metadata panel and the Files list. If something is missing, fix the script and convert again. 27. Headless mode

The same calculation engine can be run without the graphical interface. Headless mode loads workspaces, computes artifacts, applies processing configurations, and writes results to CSV - which makes it the entry point for scripted pipelines and automated processing. Errors are printed to standard error and the process exits with a non-zero status.

-tWrite a processing configuration template (template.json) to the current directory.
-rReset: delete the user configuration file and the saved window layouts.

For -w, the valid output types are the export artifact names listed in Section 17. The directory given to -w or -cmp must already exist.

27.2 Processing configuration

The optional configuration file controls the calculation. Create a starting point with -t, which writes template.json with every key and a short comment: 

{
  "spectrum": {
    "zeroPadK":          { "_comment": "Zero-padding factor (0-16).", "value": 0 },
    "apodizationWindow": { "_comment": "Rectangular, Gauss, Triangular, NortonBeer, DolphChebyshev.", "value": "Rectangular" },
    "nortonBeerFwhm":    { "_comment": "Norton-Beer FWHM (1.0-2.0).", "value": 1.5 },
    "xCorrectionMethod": { "_comment": "Hilbert or PeakFinding.", "value": "Hilbert" },
    "xUnit":             { "_comment": "cm-1, um, THz.", "value": "cm-1" },
    "yScale":            { "_comment": "lin, log10, dB.", "value": "lin" }
  },
  "allan": {
    "wavelengthDecimation": { "_comment": "1-50; 1 = full resolution.", "value": 5 },
    "xRangeMinUm":          { "_comment": "Wavelength range [um].", "value": 1.0 },
    "xRangeMaxUm":          { "_comment": "", "value": 30.0 },
    "calcBase":             { "_comment": "100% T or Spectrum.", "value": "100% T" }
  },
  "processing": {
    "workerThreads": { "_comment": "-1 = AUTO, otherwise any thread count.", "value": -1 }
  }
}

The example above is abridged: -t also writes the average, snr, and t100 sections. Every key may also be written as a plain value ("zeroPadK": 2) - the { "_comment", "value" } wrapper is what -t produces and what keeps the template self-documenting. The template is grouped by panel:

SectionKey fields
spectrumrefLaserWavelengthUm, zeroPadK, apodizationWindow, window parameters, detectorSensitivityKVperW, xCorrectionMethod, peakProminence, xUnit, yScale, yAxisMode, forcedYMin, forcedYMax

Values with a documented range are clamped. Unknown enum names warn and fall back to defaults (xCorrectionMethod and referenceSource fall back silently), and a value of the wrong JSON type aborts the run. Applying a configuration that contains a spectrum section also clears the workspace's cached spectra, so the requested artifacts are computed with the configured parameters.

27.3 Running from a script

Headless mode is designed to be called from other programs. The example below computes an average spectrum with fixed processing settings and then reads the exported CSV: 

import subprocess

import numpy as np

BIN = "fts_data_explorer"


def compute(workspace, output_type, out_dir, config=None):
    cmd = [BIN, "-w", workspace, output_type, out_dir]
    if config:
        cmd.append(config)
    subprocess.run(cmd, check=True)   # raises on a non-zero exit status


# Export the average spectrum using the pinned parameters in processing.json.
compute("sample.h5", "Average spectrum", "results/", "processing.json")

# Compare two workspaces on the reference grid (Comparator export).
subprocess.run([BIN, "-cmp", "sample.h5", "reference.h5",
                "Comparator spectra", "results/"], check=True)

# The exported CSV uses the X unit selected by the configuration.
table = np.genfromtxt("results/sample_average_spectrum.csv",
                      delimiter=",", names=True)
print(table.dtype.names, len(table))

Headless mode runs the same code paths as the graphical application, so a scripted run with the same workspace and settings produces the same results as the GUI. One difference: headless mode always processes every measurement in the workspace, while the graphical interface uses the saved selection.
